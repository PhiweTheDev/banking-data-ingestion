# DJ Data Ingestion Platform — Architecture

A portfolio project simulating a DJ data platform, demonstrating three ingestion patterns (CDC, batch, streaming) against realistic music platform data source systems, built on AWS with Terraform, and showcasing SQL, Python, and PySpark. Designed to run low-cost/serverless so it can be spun up for demos and torn down between them.

## 1. Simulated Domain

Model a retail bank with two "legacy" source systems and one real-time event source:

- **PostgreSQL** — core banking OLTP: `customers`, `accounts`, `balances`, `transactions`. This is the CDC source, since core banking systems are the classic case for change capture (balance updates, new accounts).
- **Oracle** — a bolt-on legacy system, e.g. **loans/credit risk** or **card management**. Represents the batch-only legacy estate most banks still run (nightly extracts, no CDC support, one exposed reporting schema). Run as Oracle XE in Docker/EC2 rather than RDS for Oracle, to avoid licensing cost.
- **Streaming events** — simulated real-time card transactions / ATM events / fraud-signal events, generated by a Python producer (Faker + random anomaly injection) onto Kinesis Data Streams.

A synthetic data generator (Python, `faker` + custom banking logic) seeds Postgres and Oracle and continuously emits streaming events, so the whole platform runs against believable, evolving data rather than a static dump.

## 2. Three Pipelines

### A. Change Data Capture — Postgres → Lake
Postgres (logical replication) → **AWS DMS** (CDC task) → S3 raw/bronze (Parquet, partitioned by table/date) → **Glue** (PySpark) job applies inserts/updates/deletes as an **SCD Type 2 merge** into a silver Iceberg/Delta-style table on S3 → curated gold tables queried via **Athena**.
Demonstrates: CDC semantics (insert/update/delete handling), schema evolution, upsert/merge logic in PySpark, idempotent replay.

### B. Batch — Oracle → Lake
Nightly extraction via a Python job (Oracle client / DMS full-load-only task) → S3 raw, partitioned by extract date → **Glue** PySpark job for cleansing, joins against CDC-derived customer/account tables, and data quality checks (row counts, null checks, referential integrity — Great Expectations or custom PySpark assertions) → gold tables in Athena/Glue Catalog.
Orchestrated on a schedule via **Step Functions** or a lightweight **Airflow (MWAA or self-hosted on a small EC2/Docker)** DAG — this is a good place to show orchestration and dependency management (batch job must wait for CDC merge to land before joining).
Demonstrates: batch scheduling, orchestration, SQL-heavy transformation logic, data quality gates.

### C. Streaming — Real-Time Transactions
Python producer → **Kinesis Data Streams** → **Kinesis Firehose** (or a small Flink/KDA app for windowed aggregation, e.g. rolling fraud-score or spend-velocity per account) → S3 raw → near-real-time aggregate table (Athena or DynamoDB for point lookups) → optional simple alerting (Lambda → SNS) for anomalous transactions.
Demonstrates: stream processing, windowed aggregation, low-latency path distinct from the batch/CDC paths.

## 3. Common Lake Layer

All three pipelines land in the same S3-based lake using a **medallion architecture**:

- **Bronze** — raw, immutable, as-received (Parquet/JSON), partitioned by source + date.
- **Silver** — cleaned, deduplicated, conformed schemas, CDC merges applied.
- **Gold** — business-level marts: e.g. `customer_360`, `daily_transaction_summary`, `account_balance_snapshot`. Built with SQL (Athena/dbt) — this is your best showcase for SQL skill: window functions for running balances, CTEs for dedup, MERGE statements for SCD2.

Glue Data Catalog ties it all together so Athena can query across bronze/silver/gold consistently.

## 4. Infra & Tooling

- **Terraform**, modularized: `network/`, `rds-postgres/`, `oracle-ec2/`, `dms/`, `kinesis/`, `glue/`, `s3-lake/`, `orchestration/`. Each pipeline's infra should be toggleable (e.g. via `terraform workspace` or `var.enable_streaming`) so you can spin up only what you're demoing.
- **Low-cost choices**: Aurora Postgres Serverless v2 or small RDS instance (stop when idle), Oracle XE in Docker on a t3.micro/on-demand EC2 (start/stop), Glue serverless jobs (pay per run, not always-on EMR), Kinesis with 1 shard, Athena instead of Redshift for querying. Skip MSK — Kinesis is materially cheaper for a demo and shows the same CDC/streaming concepts.
- **CI/CD**: GitHub Actions to `terraform plan/apply` and to deploy Glue job scripts — nice to show IaC + pipeline-as-code discipline.

## 5. Skills Showcase Map

- **SQL**: gold-layer mart definitions, SCD2 merge logic, window functions (running balances, rank-based dedup), data quality assertion queries.
- **Python**: synthetic data generators, DMS/orchestration glue code, Kinesis producer, Lambda functions (alerting, light transforms), Airflow DAGs.
- **PySpark**: Glue ETL jobs — CDC merge job, batch cleansing/join job, any heavier streaming aggregation if using Glue Streaming/Flink.

## 6. Suggested Repo Structure

```
banking-data-platform/
  terraform/
    modules/{network,rds-postgres,oracle-ec2,dms,kinesis,glue,s3-lake,orchestration}
    envs/dev/
  data-generator/          # Python: seeds Postgres/Oracle, streams to Kinesis
  pipelines/
    cdc/                   # Glue PySpark job(s) + DMS task config
    batch/                 # Extraction script + Glue PySpark job + Airflow DAG
    streaming/              # Kinesis consumer/Flink app + Lambda alerting
  sql/
    ddl/                   # source schemas (Postgres, Oracle)
    marts/                 # gold-layer SQL / dbt models
  tests/                   # PySpark unit tests, data quality checks
  docs/                   # architecture diagram, README, runbook
```

## 7. Build Order

1. Terraform for networking + S3 lake + Glue Catalog (foundation, cheap, always-on).
2. Postgres + data generator + CDC pipeline (DMS → bronze → PySpark merge → silver).
3. Oracle + batch pipeline (extraction → Glue job → gold, orchestrated).
4. Kinesis + streaming pipeline (producer → Firehose/aggregation → alerting).
5. Gold-layer SQL marts across all three, plus a README/architecture diagram tying it together for the portfolio write-up.

This ordering lets you demo something working after step 2 and keeps each pipeline independently completable.
